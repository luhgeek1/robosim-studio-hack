# API РобоМеры

Контракт OpenAPI 3.1 описывает операции и форматы данных действующего приложения.
Интерактивная документация: [публичный стенд](https://prooood.ru/api/docs) или
[локальный сервер](http://localhost:8000/api/docs). Все пути начинаются с /api/v1.

## Структура

| Файл | Содержимое |
|---|---|
| [openapi.yaml](openapi.yaml) | Корень контракта, пути, общие соглашения и авторизация |
| [paths](paths) | Операции по доменам: аккаунты, каталог, проекты, расчёты, имитация, отчёты и администрирование |
| [components](components) | Схемы запросов, ответов, ошибок и происхождения данных |
| [openapi.bundled.yaml](openapi.bundled.yaml) | Сгенерированная версия в одном файле |

## Доступ и основные соглашения

- Вход по почте и паролю возвращает access-токен для заголовка Authorization: Bearer. Для браузерного клиента с X-Client: web refresh-токен находится в httpOnly-cookie; обновление и выход требуют X-CSRF-Token.
- Обновление ротирует refresh-токен. Клиент должен сериализовать refresh-запросы: повтор прежнего refresh-токена отзывает сессию. Управление паролем, подключёнными сервисами и сессиями описано в [account.yaml](paths/account.yaml).
- Google, Яндекс ID и VK ID доступны при настройке соответствующего провайдера. Поток Authorization Code + PKCE, явная привязка и callback описаны в [oauth.yaml](paths/oauth.yaml); автоматического объединения аккаунтов по совпадающему email нет. Настройки сервера перечислены в [примере окружения](../../backend/.env.example).
- Личный проект принадлежит пользователю, общий — организации. Сервер проверяет текущее членство и роль. Приглашения и их принятие описаны в [organizations.yaml](paths/organizations.yaml).
- Публичные операции имеют пустое требование security. Гостевой проект использует временный токен, изолирован от других пользователей и доступен 24 часа. Ключи интеграций и их права отделены от браузерных сессий.
- Ошибки возвращаются в формате Problem с кодом error_code. Денежные суммы передаются в рублях, даты — в ISO 8601 UTC. Пагинация начинается с первой страницы.
- Значения, влияющие на расчёт, содержат происхождение provenance; расчёты сохраняют версии входов. Формулы и границы модели описаны в [методике](../METHOD.md).
- Длительные операции возвращают статус 202 и задачу. Ход выполнения доступен опросом и через SSE. Завершение и сохранение результата выполняет воркер.
- Плееры 2D и 3D используют SimulationReplay: планировку, роботов и события выбранного окна времени.

## Подготовленный пример

GET /demo/projects/{demo_key} возвращает состояние и ревизию готового примера.
После POST /auth/guest клиент вызывает POST /demo/projects/{demo_key}/open с UUID request_id
и ревизией. Повтор запроса с тем же идентификатором для того же владельца возвращает существующую копию,
сохраняя правки. Копируются параметры, планировка, сценарии и результаты имитации; экономика пересчитывается.
Подтверждение парка переносится только при совпадении физических входов.

Дальнейшая работа идёт через обычные операции проекта. Вход или регистрация с X-Keep-Guest-CSRF
переносят гостевую работу в аккаунт. Перед переносом следует дождаться завершения фоновых задач.

## Проверка и обновление

Из корня репозитория:

1. make contract-lint — проверка исходного OpenAPI.
2. make contract-bundle — обновление объединённого файла.
3. npm --prefix frontend run gen:api — генерация типов TypeScript для клиента.

Правки вносятся в исходные paths и components, а не в объединённый файл.
[Интеграционные тесты](../../backend/tests/contract_check.py) сверяют код ответа, тип содержимого
и схему тела с контрактом. Полная проверка сервера и контракта: make check.
