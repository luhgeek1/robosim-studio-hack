# RoboScope — Project Context

> Этот файл — единый контекст проекта для AI-ассистентов, которые помогают проектировать и разрабатывать продукт. Используй его как источник истины по продуктовой идее, UX, архитектуре, данным и границам MVP.

## 1. Что это за проект

**RoboScope** — B2B-сервис для предварительной оценки роботизации объекта.

Главная задача продукта — помочь бизнесу быстро ответить на вопросы:

- стоит ли роботизировать объект;
- какие робототехнические решения подходят;
- сколько роботов потребуется;
- сколько это будет стоить;
- какой экономический эффект даст внедрение;
- справится ли выбранная конфигурация с реальной нагрузкой;
- где появятся bottleneck'и и риски.

Главный демонстрационный кейс — **склад**.

Дополнительные типы объектов:
- аэропорт;
- медицинское учреждение.

В MVP полный сценарий прорабатывается прежде всего для склада.

## 2. Для кого продукт

Это **не инженерный CAD-инструмент** и не система управления промышленным оборудованием.

Целевая аудитория:

- владелец бизнеса;
- операционный директор;
- директор по логистике;
- директор по цифровизации;
- финансовый директор;
- руководитель, принимающий инвестиционное решение.

Главный UX-принцип:

> **Business first, engineering second.**

Пользователь должен быстро понимать бизнес-результат, не разбираясь в промышленной робототехнике.

## 3. Главная продуктовая идея

RoboScope не просто показывает каталог роботов.

Система строит последовательный путь:

```text
данные объекта
    ↓
нормализация
    ↓
валидация
    ↓
подбор подходящих роботов
    ↓
расчёт количества роботов
    ↓
экономическая модель
    ↓
сравнение сценариев
    ↓
имитация работы объекта
    ↓
проверка, справляется ли конфигурация
    ↓
финальная рекомендация
```

Главное отличие продукта:

> Рекомендация подтверждается симуляцией, а не остаётся статическим расчётом.

## 4. CJM

Основной пользовательский путь:

1. Пользователь создаёт проект.
2. Выбирает тип объекта.
3. Передаёт данные объекта.
4. Система автоматически понимает и нормализует данные.
5. Показывает, какие данные подтверждены, какие отсутствуют, а где использованы допущения.
6. Подбирает подходящие робототехнические решения.
7. Объясняет, почему конкретный робот подходит или не подходит.
8. Рассчитывает необходимое количество роботов.
9. Рассчитывает экономику.
10. Сравнивает сценарии роботизации.
11. Запускает симуляцию работы объекта.
12. Показывает throughput, utilization, queue, SLA и bottleneck'и.
13. Проверяет, справляется ли выбранное количество роботов.
14. Формирует итоговую бизнес-рекомендацию.
15. В будущем — генерирует PDF/отчёт для руководства.

## 5. Smart Import

Одна из ключевых функций продукта — загрузка данных в произвольном формате.

В перспективе пользователь сможет загрузить:

- XLSX;
- CSV;
- JSON;
- PDF;
- текстовые документы;
- другие структурированные и полу-структурированные корпоративные данные.

### Роль LLM

LLM используется как **интеллектуальный слой нормализации**.

Он должен:

- понять структуру входных данных;
- сопоставить пользовательские поля с внутренней моделью;
- привести единицы измерения к стандарту;
- извлечь значения из текста;
- определить отсутствующие параметры;
- отметить неоднозначные поля;
- вернуть confidence;
- сохранить связь с исходным значением.

Пример:

```text
"рабочий коридор 3200 мм"
```

превращается в:

```json
{
  "aisle_width_m": {
    "value": 3.2,
    "source_value": "рабочий коридор 3200 мм",
    "confidence": 0.98
  }
}
```

### Важно

LLM **не должен** выполнять критичные бизнес-расчёты.

LLM:
- понимает;
- сопоставляет;
- извлекает;
- объясняет.

Обычный код:
- валидирует;
- фильтрует;
- считает;
- симулирует;
- формирует итоговые KPI.

## 6. Нормализация и валидация

После LLM данные приводятся к внутренней строгой схеме.

Пример:

```json
{
  "object_type": "warehouse",
  "area_m2": 20000,
  "robotized_area_m2": 10000,
  "aisle_width_m": 3.2,
  "daily_pallets_in": 1000,
  "daily_pallets_out": 1000,
  "avg_pallet_weight_kg": 650,
  "employees": 42,
  "target_sla_percent": 97
}
```

После нормализации выполняется обычная валидация.

Рекомендуемый подход:
- Pydantic;
- business rules;
- диапазоны;
- unit normalization;
- обязательные и необязательные поля.

Если значение подозрительное, система не должна молча его принимать.

## 7. Data Confidence

Для каждого важного параметра желательно хранить:

```text
value
unit
source
source_value
confidence
is_assumption
updated_at
```

Пользователь должен видеть:

- подтверждённые данные;
- допущения;
- отсутствующие данные;
- параметры с низкой уверенностью.

Пример бизнес-отображения:

```text

⚠ Стоимость обслуживания — оценочное значение
⚠ Пиковая загрузка — допущение
```

## 8. Подбор роботов

Подбор должен быть объяснимым.

### Этап 1 — hard constraints

Робот исключается, если нарушает критичные ограничения.

Примеры:

```text
payload < required_payload
robot_width + safety_margin > aisle_width
unsupported_environment
budget_limit_exceeded
```

### Этап 2 — scoring

Оставшиеся решения получают score.

Пример факторов:

- производительность;
- стоимость;
- совместимость с объектом;
- инфраструктурная совместимость;
- зрелость решения;
- качество исходных данных;
- подтверждённые внедрения.

Точные веса могут меняться.

Пользователь должен видеть не просто score, а объяснение причин выбора.

## 9. Расчёт количества роботов

Количество роботов должно рассчитываться автоматически.

Базовая логика:

```text
required_throughput
÷
effective_robot_throughput
=
required_robot_count
```

Эффективная производительность должна учитывать:

- коэффициент загрузки;
- простои;
- зарядку;
- технологические задержки;
- резерв;
- пиковую нагрузку.

После первичного расчёта результат проверяется симуляцией.

> Математический расчёт предлагает количество роботов, симуляция проверяет его в динамике.

## 10. Экономическая модель

Основные бизнес-метрики:

- CAPEX;
- OPEX;
- TCO;
- экономия в год;
- ROI;
- Payback Period;
- FOT / затраты на персонал;
- стоимость обслуживания;
- стоимость владения на горизонте нескольких лет.

Главные сценарии:

### Current
Текущий ручной процесс.

### Purchase
Покупка роботов.

### RaaS
Robot-as-a-Service / аренда.

Интерфейс не должен выглядеть как Excel. Пользователь должен быстро понять, какой вариант дешевле, выгоднее и быстрее окупается.

## 11. Главная killer feature

Главная демонстрационная идея:

> **Экономика и симуляция связаны.**

### 2 робота

- дешевле;
- высокая utilization;
- растёт очередь;
- throughput недостаточен;
- SLA не выполняется.

### 3 робота

- выше CAPEX;
- throughput достаточен;
- очередь маленькая;
- utilization здоровая;
- SLA выполняется.

### 4 робота

- throughput ещё выше;
- очередь почти отсутствует;
- часть мощности простаивает;
- CAPEX выше;
- экономически хуже оптимальной конфигурации.

Система должна рекомендовать не самый дешёвый вариант, а:

> **минимальную конфигурацию, которая реально справляется с требуемой нагрузкой.**

## 13. 3D Digital Twin

3D — один из главных wow-элементов продукта.

Это не должен быть CAD или Blender.

Это должен быть:

> **business-oriented digital twin-lite**

Он нужен, чтобы визуально показать:

- что происходит на объекте;
- как движутся роботы;
- где появляются очереди;
- где возникает перегрузка;
- как меняется система при изменении количества роботов.

Для склада 3D может показывать:

- помещение;
- пол;
- стеллажи;
- Receiving;
- Storage;
- Picking;
- Shipping;
- buffer zones;
- charging zone;
- роботов;
- паллеты;
- маршруты;
- очереди;
- bottleneck'и.

## 14. Что должно происходить в 3D

Пользователь меняет:

```text
2 / 3 / 4 robots
```

и одновременно должны меняться:

- количество роботов на сцене;
- их загрузка;
- частота движения;
- длина очереди;
- загрузка зон;
- bottleneck visualization;
- KPI;
- throughput;
- utilization;
- SLA;
- CAPEX;
- ROI;
- Payback.

Также желательно:

```text
Normal Load / Peak Load
```

При Peak:
- больше задач;
- выше utilization;
- длиннее очереди;
- выше вероятность bottleneck;
- SLA может ухудшаться.

## 15. 3D не должно считать бизнес-логику

Frontend 3D-сцена должна быть визуализатором.

В реальной архитектуре:

```text
Simulation Engine
      ↓
simulation events / states
      ↓
API
      ↓
3D frontend
```

Пример события:

```json
{
  "time": 35,
  "robot_id": "R1",
  "state": "moving",
  "from": "receiving",
  "to": "storage",
  "queue": 7
}
```

## 16. Simulation Engine

Предпочтительный подход:

- Python;
- SimPy или собственная event-based модель.

Симуляция должна учитывать хотя бы:

- очередь задач;
- свободных роботов;
- движение между зонами;
- время загрузки;
- время разгрузки;
- занятость;
- простои;
- зарядку на упрощённом уровне;
- throughput;
- utilization;
- SLA.

Не нужна физически точная модель. Главное — причинно-следственная связь между конфигурацией и KPI.

## 28. Demo moment

Один из главных моментов защиты:

1. Открывается конфигурация из 3 роботов.
2. Система показывает SLA около 98%.
3. Пользователь переключает на 2 робота.
4. Один робот исчезает с 3D-сцены.
5. Остальные роботы начинают работать почти постоянно.
6. Очередь растёт.
7. На сцене появляется bottleneck.
8. SLA падает.
9. Система пишет:

```text
2 робота не обеспечивают пиковую нагрузку.
```

10. Пользователь возвращает 3 робота.
11. Очередь уменьшается.
12. SLA восстанавливается.
13. Появляется вывод:

```text
3 робота — минимальная конфигурация,
которая стабильно выполняет SLA.
```

Главная связь:

```text
investment
↔
operations
↔
simulation
↔
business result
```

## 31. Главная формулировка продукта

Коротко:

> **RoboScope — сервис, который по данным объекта подбирает роботизацию, считает экономику и проверяет выбранную конфигурацию через интерактивную симуляцию.**

Ещё короче:

> **Какой робот → сколько → выгодно ли → справится ли.**

## 32. Правила для AI-разработчика

При работе с этим проектом:

1. Не превращай продукт в инженерный инструмент.
2. Не перегружай интерфейс KPI и таблицами.
3. Сохраняй business-first подход.
4. Любая рекомендация должна быть объяснима.
5. 3D должно помогать понять бизнес-проблему.
6. 3D не должно быть просто декоративной сценой.
7. LLM не должен выполнять детерминированные расчёты.
8. Все mock-значения должны быть явно отделены от реальных расчётов.
9. Архитектуру делать расширяемой, но не переусложнять MVP.
10. Любой новый экран должен отвечать на конкретный пользовательский вопрос.
11. Любая сложная метрика должна иметь простое человеческое объяснение.
12. Приоритет — эффектный, понятный и кликабельный хакатонный MVP.

## 33. Definition of Success

Прототип успешен, если пользователь без объяснений команды может за несколько минут понять:

1. какой объект анализируется;
2. какие данные система знает;
3. какой робот рекомендован;
4. сколько роботов нужно;
5. сколько это стоит;
6. когда окупится;
7. что произойдёт при 2 / 3 / 4 роботах;
8. где возникает bottleneck;
9. почему рекомендуется именно выбранная конфигурация;
10. стоит ли двигаться дальше с проектом роботизации.

## 34. Итоговое продуктовое направление

Это не:

```text
каталог роботов
```

и не:

```text
3D-визуализатор склада
```

и не:

```text
ROI-калькулятор
```

Это единый decision-support продукт:

```text
DATA
  ↓
MATCHING
  ↓
ECONOMICS
  ↓
SIMULATION
  ↓
DECISION
```

**Главная ценность — связать техническую возможность роботизации с понятным бизнес-решением.**
