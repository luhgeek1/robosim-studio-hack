## Суть одной фразой

Веб-платформа для **экспресс-предынвестиционной оценки роботизации объекта**: каталог роботов → объяснимый подбор
под параметры объекта → расчёт количества и экономики (как сейчас / покупка / RaaS) → 2D-имитация, которая
**подтверждает** расчётную производительность → отчёт PDF/Excel. Не заменяет проектирование, а даёт обоснованную гипотезу
для перехода к ТЭО и пилоту (ТЗ 1, 2).

**Заказчик:** Департамент предпринимательства и инновационного развития Москвы и АНО «ФЦ БАС» (Федеральный центр
беспилотных авиационных систем). Лучшее решение планируют пилотировать с реальными клиентами (ТЗ 10, Q&A).

**Эксперты от ФЦ БАС:** Елисеев Сергей (зам. рук. Центра аналитики и развития), Некраш Алина (рук. отдела
экономического моделирования), Баранов Денис (гл. аналитик), Шиманский Ян (ведущий аналитик). На Q&A отвечали
Михаил Калюжный (отдел экономического моделирования) и Ян Шиманский. Жюри — экономисты и аналитики,

## Пользовательский путь (ТЗ 2.2) — все 8 шагов обязательны

1. **Выбор отрасли и объекта:** склад / аэропорт / медучреждение (+ «другое»). Для базовых — демо-данные.
2. **Параметры:** ручной ввод или загрузка Excel/CSV по шаблону; проверка заполненности, формата, диапазонов.
3. **Подбор:** применимые типы роботизации → конкретные продукты → причины включения и исключения.
4. **Сравнение** решений по единым техническим, эксплуатационным и экономическим характеристикам.
5. **Экономика:** состав оборудования, CAPEX, OPEX, TCO, годовой эффект, окупаемость, ROI + видимые формулы и предпосылки.
6. **What-if:** меняем параметры, сравниваем базовый и альтернативные сценарии в одной таблице.
7. **Визуализация:** 2D-схема, роботы, KPI. Должна **подтверждать расчёт**, а не быть декоративной анимацией.
8. **Сохранение и экспорт:** PDF + Excel (или эквивалентные форматы).

## Функциональные требования — чек-лист

**Роли и проекты (3.1)**
- Гость (каталог + демо-расчёт без сохранения чувствительных данных), пользователь, администратор. Вендор — опционально.
- Пользователь: создать / редактировать / копировать / сохранить / удалить проект; ≥3 сценариев в проекте.
- Админ: каталог, справочники, параметры по умолчанию, источники данных.
- Повторное открытие проекта и **воспроизведение расчёта с версией исходных данных и расчётной модели** (3.1.5).

**Параметры объекта (3.2)**
- Свой набор обязательных и дополнительных полей на каждый тип объекта (минимальные списки в ТЗ 3.2.1).
- Формы + импорт Excel/CSV по шаблону; валидация типов, единиц, обязательности, диапазонов.
- Показывать значения по умолчанию **и источник каждого норматива**. Справочники расширяемы.

**Каталог (3.3)**
- Иерархия: отрасль → тип объекта → процесс → тип решения → продукт.
- Загрузка таблицы организатора; дополнение из открытых источников с **ссылкой, датой и признаком подтверждённости**.
- Ручное добавление и редактирование через админку (парсинг — плюс, но не замена). Обновление по запросу, по расписанию — плюс.
- Фильтр, поиск, сортировка, сравнение.
- Группы характеристик: идентификация · технические (грузоподъёмность, габариты, скорость, производительность,
  автономность, точность позиционирования, навигация, условия эксплуатации) · инфраструктура (покрытие, проходы, зарядка,
  связь, интеграция, сервис) · экономика (оборудование, ПО, внедрение, обслуживание, модель приобретения, срок службы) ·
  применимость (процессы, типы объектов, ограничения, кейсы) · качество данных (источник, дата, полнота, подтверждённость).

**Подбор (3.4)**
- Список применимых типов и продуктов по параметрам объекта и ограничениям продукта.
- Для каждого: причины соответствия, ограничения, недостающие данные.
- Жёсткое ограничение нарушено → **не рекомендовать**. Данных не хватает → «требует проверки».
- Можно вручную добавить продукт в сравнение с предупреждением (после автоподбора, Q&A).
- **Объяснимое ранжирование:** критерии и вклад факторов в итоговую оценку.

**Экономика (3.5)**
- Минимум: число роботов и вспомогательного оборудования; CAPEX по статьям; годовой OPEX и его изменение против базы
  (экономия ФОТ и др.); чистый годовой эффект; простая окупаемость; ROI; TCO на горизонте ≥5 лет.
- Рекомендуемые формулы:
  - роботы = пиковая потребность / (производительность × загрузка × доступность) + резерв;
  - CAPEX = оборудование + инфраструктура + ПО + интеграция + ПНР + обучение + резерв;
  - OPEX = сервис + лицензии + электроэнергия + связь + расходники + ремонт + персонал эксплуатации;
  - эффект = снижение затрат + доп. доход или предотвращённые потери − доп. OPEX;
  - окупаемость = CAPEX / эффект; ROI (классический, см. Q&A ниже); TCO = CAPEX + ΣOPEX + замены компонентов.
- Пользователь меняет: стоимость персонала, режим работы, производительность, цену оборудования, стоимость обслуживания,
  загрузку, горизонт. Автозначения можно поправить вручную **с фиксацией изменения**.
- ≥3 сценариев; **чувствительность минимум к трём параметрам** для каждого сценария.
- Рекомендация не только по жёсткому порогу окупаемости: число + риски + интерпретация (например, <3 / 3–5 / >5 лет).
- Все формулы, единицы, источники и допущения видны в интерфейсе или отчёте.
- **Недокументированные коэффициенты запрещены** (3.5.1).

**Имитация (3.6)**
- 2D-схема: зоны, маршруты, роботы, точки операций и зарядки. 3D — опционально.
- Использует параметры сценария и подтверждает расчётную производительность.
- Старт / стоп / перезапуск, скорость воспроизведения, выбор сценария.

**Результаты (3.7)**
- Дашборд сравнения сценариев + краткое заключение.
- Отчёт: параметры объекта, решения, состав оборудования, экономика, ограничения, источники, дата расчёта.
- PDF + Excel/CSV; экспорт или сохранение визуализаций.
- Явная пометка: «предварительная оценка, требует верификации при обследовании объекта».

**Интеграции (3.8)**
- API импорта объектов, каталога и нормативов. Все API документированы (OpenAPI).
- Описать возможные интеграции с WMS, ERP, 1С, мониторингом оборудования и продуктами ФЦ БАС.
- Проверка по госреестрам и расчёт мер господдержки — дополнительная функция.

## Нефункциональные требования (ТЗ 4)

- Веб, клиент и сервер раздельно; Docker + docker-compose; реляционная или документная СУБД; OpenAPI.
- Работает на заранее загруженных данных: внешние источники не должны быть точкой отказа демо.
- 50 одновременных пользователей; экономика ≤10 с; симуляция ≤60 с со статусом выполнения.
- Роли, хэши паролей, изоляция проектов, HTTPS при размещении, удаление проекта вместе с файлами.
- Только русский интерфейс; ключевой путь проходится без инструкции; у полей единицы, подсказки, примеры;
  ошибки понятны и подсказывают, как исправить; работает от 1366×768.

## Разъяснения организаторов, которые меняют реализацию

**Данные**
- `catalog_export_v4.csv` — актуальный файл (в дополнениях опечатка про v5). Все выданные файлы эталонные.
- Дубли в каталоге **не объединять**: это модификации и комплектации или разные отрасли (цена ПО и внедрения зависит от отрасли).
  Для складов роботы обычно относятся к отрасли «торговля»; промышленные AMR на 15–35 т для склада почти не подходят.
- Цены каталога **с НДС** и без доставки, ПНР и глубокой интеграции (Доп. 6). Считать всё в единой базе: ФОТ с
  начислениями, то есть полные затраты работодателя.
- Датасеты демонстрационные, их поля формулами не связаны (пример: в медучреждении 1950 порций против 1599 расчётных).
  Можно брать производное значение, главное — внутренняя согласованность наших формул.
- Шум, ровность пола, мощность зарядки и т.п. можно закрывать допущениями, если явно их описать (Доп. 5).

**Экономика**
- Окупаемость — классическая простая (можно дополнительно дисконтированную). Амортизация не вычитается повторно:
  она нужна только для бухгалтерского результата, по желанию.
- ROI — классический, **с вычетом CAPEX**: (накопленный эффект − CAPEX) / CAPEX. Отклонение от буквы ТЗ не штрафуют.
- Состав CAPEX и OPEX (операторы, диспетчеры, интеграция, ПНР, деградация батарей и т.п.) — **наши допущения**.
  Оценивают их разумность и полноту: учесть всё, что заметно влияет на результат.
- Горизонт по умолчанию из датасета (склад — 5 лет, аэропорт и медучреждение — 7), можно сделать настраиваемым.
  Учитывать срок службы роботов (замены внутри горизонта).
- Обязательно AS-IS против TO-BE. TO-BE — покупка; аренда или RaaS — наша дополнительная опция с нашими допущениями.
  Мин/макс-варианты — по желанию (доп. сценарии или динамические предпосылки).
- Базовое финансирование — собственные средства; кредит или лизинг — опционально, со ставками и графиком (Доп. 2.1).

**Подбор**
- Сравнение по группам ТТХ. Каталог: загрузка файла, ручные карточки, поиск, фильтр, сортировка, сравнение,
  источник у каждой характеристики. Полноценный маркетплейс не нужен.
- Нужна проверка **физической и инфраструктурной совместимости**: грузоподъёмность, габариты, проходы, двери, радиус
  поворота. Подтверждённое несоответствие → исключить. Ответ «подходящих решений нет» допустим.
- Сначала автоподбор, потом ручной выбор. Эталонных ответов нет: качество оценивают по фильтрации, учёту ограничений,
  объяснимости, прозрачности расчёта, допущениям и тестам.

**Границы**
- **Один тип объекта — в полную глубину**, остальные два — на уровне выбора, параметров и доступных решений.
- Фокус на наземных роботах (БРС). Дроны (БАС) — бонус, если применение осмысленное.
- С robot.moscow кейс не связан, ориентироваться на него не нужно: продукт самостоятельный.
- Гостю можно дать what-if для вовлечения: необязательно, но может выделить.
- Загрузка аудита или ТЗ объекта с автоизвлечением параметров допустима (это продуктовый выбор).

**Симуляция**
- Должна быть **больше, чем формула «производительность × время» + случайная анимация**: должна давать что-то
  логике расчёта. **Проверять будут по коду**, участвует ли имитация в вычислениях.
- Глубина на наше усмотрение: зарядка, проходы и т.п. приветствуются. Важнее вклад в модель, чем красота (хотя красота «цепляет глаз»).
- Формат экспорта визуализации — на наше усмотрение, распространённые форматы.

**Стек**
- Любой обоснованный, лучше open source. Отечественные LLM и локальный запуск не обязательны.
  ML и оптимизация — плюс. Во внешние API нельзя отдавать реальные ПДн и сведения ограниченного доступа.
