# Решения

Журнал решений команды. Формат записи: **решение / почему / отвергнутые альтернативы**. Новые записи — сверху.
Факты от организаторов сюда не пишем, они в `docs/CASE_BRIEF.md`. Здесь только то, что выбрали мы.
Решение можно пересмотреть: новая запись со ссылкой на старую, старую не удаляем.

## Принятые

### D-018 · 2026-09-23 · MVP фронта делаем мы на новом каркасе, v0 уходит в legacy
- **Решение.** Новый `frontend/` на стеке `docs/ENGINEERING.md` §5 (из `template/frontend` переносим только клиент API
  с refresh и CSRF, авторизацию и компоненты shadcn). Экраны MVP — на живых эндпоинтах контракта 0.3.0, план и карта
  экранов — `docs/FRONTEND.md`. Фронтендер потом рестайлит: логика данных отделена от `ui/`.
  - v0 переносится в `legacy/frontend-v0/` (донор стилей и графиков, удалить до сдачи); 3D-карта фронтендера
    сохранена тегом `v0-twin-3d` — основа для 3D-вида в P2 на событиях `SimulationReplay`. D-016 закрыт.
  - Экраны без бэкенда (имитация, отчёты, демо, админка) видны в навигации как «скоро».
- **Почему.** v0 работает только со старым API и показывает декоративную анимацию (случайные маршруты, KPI
  со «шумом») — жюри проверит по коду, что имитация влияет на расчёт. До сдачи 5 дней; бэкенд готов на 67 из 108
  операций, и без фронта его не видно.
- **Альтернативы.** Ждать фронтендера на каркасе — нового кода в репозитории нет, риск не успеть. Адаптировать v0
  к новому API — нет роутинга, авторизации и половины экранов, дешевле собрать заново.

### D-017 · 2026-09-23 · Планировка склада — схема из параметров и граф маршрутов для цикла и имитации
- **Решение.** Генератор строит схему склада (не CAD) по параметрам объекта и нормативам категории `layout`.
  Каждый размер — шаг трассы `derivation` с формулой и источником. Состав схемы: здание, ярусы, проходы и поперечные
  проезды, ворота, зона G2P со станциями, зарядки, упаковка. По графу Дейкстрой считаются средние маршруты
  (`stats.avg_route_m`), и в расчёт они входят как входы вида `layout`.
  - **Порядок источников длины маршрута:** замер пользователя (`pallet_route_length_m`) → планировка → норматив
    (200 м ФЦ БАС, 40 м G2P).
  - **Паллеты:** маршрут — среднее по приёмке, отгрузке и внутренним перемещениям, взвешенное объёмами
    (выражение в справочнике процесса). Хранение случайное: ячейки взвешены по паллетоместам.
  - **Схема по умолчанию:** U-flow, приёмка и отгрузка на одном фасаде. Ворота стоят по центру своей половины блока
    стеллажей, зарядки — между приёмкой и отгрузкой. Число ворот — по пиковому потоку паллет, если в параметрах его нет.
    Паллетные роботы не срезают путь через зону G2P.
  - **Демо-склад создаётся с планировкой.** Перегенерация или правка повышает версию проекта, и расчёты становятся stale.
    После правки в редакторе длины рёбер пересчитываются по координатам, а `generated` = false.
  - **Подложка-план** хранится в Postgres (`stored_files`), чтобы `docker compose up` не требовал S3.
- **Почему.** Норматив 200 м — маршрут чужого объекта. Схема даёт маршрут этого склада, а граф с ширинами и
  вместимостями рёбер нужен имитации (D-007). На демо-складе маршрут 95 м вместо 200 м, и паллеты окупаются
  за 3 года (`docs/DATA.md`).
- **Альтернативы.**
  - Оставить норматив и множитель √площади из v0 — это не маршрут, отвергнуто.
  - Хранение по классам ABC — позже, если будет время: оно даёт более короткий маршрут, а случайное хранение
    консервативно.
  - Импорт DWG/DXF — вне рамок, у нас подложка и редактор.

### D-016 · 2026-09-22 · Улучшение существующей 3D-карты по запросу пользователя (закрыто D-018)
- **Решение:** доработать 3D в текущем `frontend/`: один контроллер камеры, ручные ракурсы, панорамирование,
  масштаб и более читаемая сцена. Геометрия остаётся иллюстративной, расчётные модели не меняются.

  развивать визуализацию v0. Обязательная 2D-имитация по D-006 остаётся в плане.
- **Альтернативы:** заменить экран на 2D сейчас — не соответствует текущему запросу.

### D-015 · 2026-09-22 · Экономическая модель сценария
- **Решение.** Сценарий — портфель «процесс → продукт → N». Все суммы с НДС (единая база, Q&A 16.09), до налога
  на прибыль.
- **Годовые статьи** (год 1).
  - CAPEX (покупка, лизинг): роботы, зарядки и станции G2P, доставка, лицензии RMS, ПНР, статьи объекта из справочника
    (`site_costs`: интеграция, разметка, Wi-Fi, лифты, обучение), резерв CAPEX.
  - CAPEX (RaaS): подключение + статьи объекта.
  - OPEX: сервис, расходники, подписка ПО, АКБ (в среднем за год), электроэнергия, персонал эксплуатации (не меньше
    минимума на объект), связь; у RaaS — абонентская плата: своя ставка из ТТХ или max(доля цены, норматив).
- **Эффект.** Высвобождение = ФОТ процесса × доля высвобождения × доля пика, закрытая парком. Сверху его ограничивает
  потолок: человеко-часы самого объёма работ при ручном выполнении. Выработка человека берётся из норматива (уборка,
  отбор); для транспорта — не выше цикла робота. Причина потолка: численность в датасете не связана с объёмами.
  Из высвобождения вычитаются OPEX роботизации и проценты по кредиту или лизингу (Доп. 2.1).
- **Загрузка за рейс.** Задаётся выражением в справочнике процессов: порции отделения, контейнер белья, сцепка тележек
  с учётом их тары. Тягач заменяет только водителя, поэтому его доля высвобождения умножается на `tow_driving_share`.
- **Денежный поток** — помесячный.
  - Внедрение без эффекта, затем разгон: высвобождение растёт линейно, OPEX роботов идёт сразу полностью.
  - Индексация: ФОТ — по зарплатам, прочее — по инфляции.
  - Замены: АКБ по интервалу, парк — по сроку службы; остаточная стоимость (линейно) входит в последний месяц.
  - Кредит и лизинг — аннуитет по номинальной ставке, метод ФЦ БАС. RaaS — плата с запуска; при выкупе после договора
    переходим на OPEX владения.
- **Метрики.**
  - Окупаемость по ТЗ = CAPEX / годовой эффект; дисконтированная — по потоку.
  - ROI = накопленный поток / CAPEX (Q&A: с вычетом CAPEX). NPV и IRR — по месячному потоку.
  - TCO = CAPEX + Σ(оставшийся ФОТ + OPEX + плата RaaS + проценты + замены) за горизонт; у базы — ФОТ всего объекта.
  - Амортизация и налог — только справочно (Доп. 2.2, Q&A).
- **Вердикт** — по интервалам-нормативам (3 / 5 / 7 лет) с проверкой NPV. Риски — по правилам (бюджет, срок службы,
  NPV, покрытие пика, статус продукта, нет имитации, «паспорт против физики»).
- **Калибровка** — модельные кейсы ФЦ БАС (`seeds/data/calibration.yaml`) пересчитываются нашими формулами
  и нормативами, расхождение показывается по статьям.
- **Почему.** ТЗ 3.5 и Доп. 2 целиком. Каждая строка — формула с входами и источниками. Экономика не зависит от того,
  насколько согласован датасет.
- **Альтернативы.**
  - Годовая модель без помесячного потока — теряет внедрение, разгон и точные сроки замен.
  - Высвобождение без потолка — давало окупаемость 0,3 года на данных аэропорта.

### D-014 · 2026-09-22 · Формулы в данных, пустой проект против демо, распределение персонала
- **Решение:** спрос процессов (`demand.per_day / hours_per_day / peak_factor`) и межполевые проверки формы описаны
  в YAML справочника на мини-языке `app/engine/expressions.py`: только имена параметров и нормативов, `+ − × ÷`,
  сравнения, `min/max/coalesce`; **числовые литералы запрещены парсером** — коэффициент не спрятать в формулу (ТЗ 3.5.1).
  Проценты из датасета приходят в формулы долями. Общие группы персонала делятся между процессами долями
  `labor_allocation` с обоснованием (сумма по группе ≤ 1, проверяется при сидировании) — ФОТ не задваивается.
  Пустой проект не подставляет значения демо-объекта организатора в обязательные поля (они описывают один конкретный
  склад) — пользователь вводит свои; допущения команды действуют везде. Демо-проект берёт все значения датасета
  со статусом `default` и источником-листом.
- **Почему:** новый тип объекта = только данные; жюри видит формулу и источник каждого числа; честная панель доверия.
- **Альтернативы:** функции спроса в коде на каждый процесс — отвергнуто (код меняется при каждом объекте).

### D-011 · 2026-09-22 · Контракт-first: фронтенд и бэкенд разрабатываются по OpenAPI
- **Решение:** источник истины по API — `docs/api/openapi.yaml` (+ файлы в `docs/api/`). Фронтенд разрабатывается
  по нему сразу в полном объёме, с mock-сервером (Prism) там, где бэкенд ещё не готов. Бэкенд обязан соответствовать
  контракту; контрактные тесты сверяют реальную схему FastAPI с YAML. Изменение контракта = правка YAML + запись
  в `docs/CONTRACTS.md` → «Изменения».
- **Почему:** фронтендер работает параллельно и быстрее, чем бэкенд; без зафиксированного контракта он остановится
  или напишет под моки, которые потом не совпадут.
- **Альтернативы:** генерировать контракт из кода по ходу — фронт ждёт бэкенд, отвергнуто.

### D-008 · 2026-09-22 · LLM — везде, где даёт ценность, но никогда в расчётах
- **Решение:** LLM используем для умного импорта, обогащения ТТХ каталога из открытых источников, объяснений
  и ответов на вопросы по трассе расчёта, текста выводов отчёта, проверки допущений на правдоподобие.
  Основной провайдер — Gemini через Google AI Studio (есть кредит $300), запасной — OpenAI. Провайдер за абстракцией,
  у каждой LLM-функции есть детерминированный fallback: демо у жюри должно работать без интернета и ключей.
  Всё, что LLM предлагает и что влияет на числа, получает статус `llm_suggested` и требует подтверждения человеком.
- **Почему:** ТЗ: ML — плюс «при наличии обоснованной задачи»; Q&A: внешние LLM допустимы, ПДн отдавать нельзя
  (у нас их нет). Бэкенд на fly.io за пределами РФ, доступ к Gemini есть.
- **Альтернативы:** локальная LLM — не обязательна (Q&A), дорого по времени.

### D-007 · 2026-09-22 · Глубина симуляции — максимальная, симуляция определяет итоговое число роботов
- **Решение:** дискретно-событийная симуляция (SimPy) на графе планировки, сгенерированной из параметров объекта:
  задачи по часовому профилю, роботы с состояниями, пропускная способность проходов (заторы), зарядные станции
  и батарея, станции отбора как ресурсы, отказы, стресс-тесты (пиковый день, отказ робота, +% объёма),
  диагностика узкого места. Итоговое `N` в сценарии и экономике берётся из симуляции (`count_result.source = simulated`),
  аналитический расчёт — стартовая точка поиска.
- **Почему:** Q&A: «симуляция должна быть больше, чем формула и анимация; проверим по коду». Это же наш главный
  отрыв («паспорт против физики»).
- **Альтернативы:** очередь без пространства, как в v0 — не даёт заторов и узких мест, отвергнуто.

### D-006 · 2026-09-22 · Визуализация — 2D-карта на журнале событий симуляции

### D-005 · 2026-09-22 · Главный объект — склад, остальные — «витрина» с ростом
- **Решение:** склад — в полную глубину (все процессы, симуляция, отчёт). Аэропорт и медучреждение — параметры,
  подбор, аналитическая экономика без симуляции; наращиваем после склада, план на них согласуем отдельно.
- **Почему:** Q&A: «инвестировать в глубину одного»; у склада больше всего данных и решений в каталоге.

### D-004 · 2026-09-22 · Основа кода — новый каркас из `template/`, доменная логика v0 переносится с переработкой
- **Решение:** бэкенд, фронтенд, инфраструктура (docker, nginx/caddy, fly, CI) берутся из `template/`
  (FastAPI + PostgreSQL + Alembic + JWT/RBAC + Redis/воркеры; React FSD + shadcn + TanStack Query).
  Из v0 переносим смысл сервисов (реестр параметров, парсеры, нормализатор, подбор, SimPy-ядро, экономика),
  но переписываем под стандарт `docs/ENGINEERING.md`. Известные слабости шаблона (толстые модули, Pydantic ↔ ORM без DTO,
  RBAC без гранулярности) исправляем при переносе, не копируем.
- **Почему:** 25% баллов — техническая проработка: роли, изоляция, миграции, Postgres уже есть в шаблоне;
  v0 — SPA без роутинга на SQLite без авторизации.
- **Альтернативы:** доработать v0 — отвергнуто (см. выше).

### D-003 · 2026-09-22 · Качество кода — senior-level, стандарт в `docs/ENGINEERING.md`
- **Решение:** слоистая архитектура с явными DTO и мапперами, модули до ~300 строк, все числовые нормативы в

### D-001 · 2026-09-19 · Структура контекста
- **Решение:** `case/` — первоисточники только для чтения; `docs/` — выжимки, решения, статус; `AGENTS.md` — точка
  входа для любых ассистентов; `CLAUDE.md` импортирует `AGENTS.md`. Доки прототипа — в `docs/archive/`.
- **Почему:** команда работает в разных ассистентах; один большой файл контекста устаревает и смешивает факты с гипотезами.
