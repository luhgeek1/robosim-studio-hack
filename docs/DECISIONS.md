# Решения

Журнал решений команды. Формат записи: **решение / почему / отвергнутые альтернативы**. Новые записи — сверху.
Факты от организаторов сюда не пишем, они в `docs/CASE_BRIEF.md`. Здесь только то, что выбрали мы.
Решение можно пересмотреть: новая запись со ссылкой на старую, старую не удаляем.

## Принятые

### D-027 · 2026-09-24 · Финальное название продукта — «РобоМера»
- **Решение.** Продукт называется «РобоМера», технический slug — `robomera`. Название используется в интерфейсе,
  API, отчётах, экспортируемых файлах, демо-адресах и конфигурации окружения.
- **Почему.** Короткое русское имя отражает основную ценность платформы: измеримую экспресс-оценку роботизации
  объекта. Оно понятно без расшифровки и помещается в существующую шапку интерфейса.
- **Альтернативы.** Англоязычное рабочее имя не объясняло назначение продукта; «РобоПотенциал» длиннее и хуже
  работает как компактный бренд в интерфейсе.

### D-026 · 2026-09-24 · Каждый обязательный параметр объекта влияет на оценку
- **Решение.** Обязательный параметр (минимальный состав ТЗ 3.2.1) обязан менять расчёт, подбор, затраты, риск или
  проверку данных; иначе он явно помечен описательным с причиной (`descriptive_params` в справочнике: тип и режим
  больницы, площадь перрона). Тест роняет сборку, если обязательное поле ни на что не влияет.
  - **Механизмы движка:** габариты «1200×800×1600» читаются формулами как длина, ширина, высота; значение списка
    может нести число (лифты с API — 1); правило подбора с условием `when` (допуск на перрон — только если нужен)
    и правило об объекте без ТТХ (стеллажи, ровность пола); дополнительные операции рейса процесса
    (`cycle_extras`: лифт по этажности, обеззараживание); риски мощности зарядок и норматива доставки.
  - **Правила** по заметкам организатора в датасете: WMS («обязательно для роботизации» → внедрение в CAPEX),
    стеллажи-поды по числу SKU, тип стеллажей и ровность пола для автоматического хранения, длина паллеты в
    планировке, допуск на перрон и защита IP для открытых зон, СКУД по режимным зонам и отделениям, лифты
    по этажности и API, обеззараживание («учитывается в OPEX»), минимум рейсов на точку, цель SLA — из параметра.
- **Почему.** Аудит 23.09 нашёл 20 обязательных полей без влияния, а часть затрат была «зашита» по датасету
  («СКУД есть», «BMS частично») и не менялась от ввода. Жюри оценивает учёт ограничений; организатор в датасете сам
  указал, как поля должны влиять.
- **Альтернативы.** Сделать поля необязательными — противоречит ТЗ 3.2.1; оставить описательными — «ничего не
  изменится, если нет WMS» — слабое место на защите.

### D-024 · 2026-09-23 · Имитация буксируемых сцепок; в скоринге подбора — экономика, а не цена железа
- **Решение.**
  - **Тягач в имитации** (`ProcessModel.TOW_TRAIN`) работает так же, как формула расчёта: паллеты копятся в сцепку
    у ворот (для отгрузки — у ворот назначения), тягач цепляет сцепку один раз, везёт её по пути паллетных роботов
    и отцепляет один раз; рейс — `units_per_trip` паллет из трассы. Неполная сцепка уходит через
    `sim_tow_dispatch_wait_min` (10 мин) после первой паллеты. Перебор флота и «расчёт против имитации» работают,
    как для AMR. На демо-складе: по циклу 3 тягача, по имитации 2.
  - **Критерий «Экономика решения»** вместо «Стоимости конфигурации»: баллы по месту кандидата процесса по NPV
    быстрой оценки (покупка решения с затратами объекта), 100 у лучшего, 0 у последнего. Веса: экономика 0,35,
    производительность 0,15 (было 0,25 и 0,25).
- **Почему.** Подбор ставил первым тягач RoboCV: 4 машины и 10 млн CAPEX давали 100 баллов и за производительность,
  и за стоимость, хотя тягач высвобождает только водителей (люди грузят тележки) и не окупается. Число роботов уже
  входит в NPV, поэтому равные веса считали его дважды. Место, а не величина NPV — чтобы один сильно убыточный
  кандидат не сжимал шкалу и меньший убыток всё равно был выше, когда не окупается никто.
- **Альтернативы.** Исключать неокупаемые решения из подбора — подбор отвечает на «подходит ли технически»,
  экономику показывает, но не фильтрует; линейная шкала между худшим и лучшим NPV — зависит от выброса.

### D-023 · 2026-09-23 · «Объём операций» в чувствительности двигает и персонал процессов
- **Решение.** Драйвер «Объём операций» (торнадо, тепловая карта, Монте-Карло) масштабирует не только суточные
  объёмы процессов сценария, но и численность групп персонала, занятых в этих процессах.
- **Почему.** При неизменной численности +20 % объёма означали бы, что сегодняшние люди справляются с лишней работой
  бесплатно, а роботов под неё нужно больше. Тепловая карта «ФОТ × объём» показывала падение NPV с ростом объёма —
  для экономистов жюри это ошибка модели. Теперь «как сейчас» и «с роботами» обрабатывают один и тот же объём.
- **Альтернативы.** Отдельные драйверы «объём» и «численность» — непонятно пользователю и снова дают несогласованные
  точки; пересчёт численности по нормам выработки — в датасете численность не связана с объёмами (`docs/DATA.md`).

### D-025 · 2026-09-23 · Данные и логика фронта из ветки `frontend-rework` — в `main`, дизайн остаётся за `main`
- **Решение.** Из `frontend-rework` в `main` перенесены данные и логика, вид экранов `main` не менялся.
  - **Имитация.** 2D-схема (`LayoutMap` со слоем роботов) и 3D-двойник строятся из планировки прогона (`LayoutPlan`)
    или проекта и двигают роботов только по журналу событий (`entities/simulation/playback.ts`, один час для 2D,
    3D и KPI). Это уточняет D-020: 3D больше не типовая сцена со случайными маршрутами. Проверяется рабочий парк
    (`simulated ?? analytic`), резерв показан отдельно. Стресс-тесты «+20 % объёма» и «отказ робота на 2 ч»
    взяты из `docs/PRODUCT.md`, заторы — из `/heatmap`. Перебор флота идёт и для вариантов RaaS и лизинга
    с тем же процессом, затем сценарии пересчитываются.
  - **Отчёт** (ТЗ 3.7): PDF, Excel с формулами и JSON как фоновая задача, пометка «предварительная оценка»,
    снимок плеера в PDF (`uploadSimulationVisual` → `visual_ids`).
  - **Подбор:** `missing_data` с `why_needed` (ТЗ 3.4.3), ручное добавление исключённого решения с показом причин
    (ТЗ 3.4.4).
  - **Экономика:** покупка, RaaS и лизинг собираются одной кнопкой (ТЗ 3.5.5), Монте-Карло с seed 1, как в отчёте.
- **Почему.** В `main` 3D-двойник двигался случайно (нарушение D-006), шаг «Отчёт» был заглушкой, не было 3.4.3,
  3.4.4 и 2D-плеера (3.6). Дизайн `main` пользователь ведёт сам.
- **Альтернативы.** Слить `frontend-rework` целиком — отвергнуто: другой дизайн, доля заполненности данных
  считалась на фронте, устаревшие расчёты не пересчитывались, часть глубины `main` терялась (планировка с выводом
  геометрии, IRR и строки сравнения с сервера, веса критериев).

### D-022 · 2026-09-23 · Контракт проверяется на каждом ответе тестов; инварианты — на всех типах объектов
- **Решение.** Тестовый клиент (`backend/tests/conftest.py`) сверяет каждый ответ интеграционных тестов с
  `docs/api`: код, тип содержимого и схему тела (jsonschema по склеенному контракту, `tests/contract_check.py`).
  Расхождение роняет тест. Коды 400/401/403/404/422/429 может вернуть любая операция с телом `Problem`, это
  правило записано в `docs/api/README.md`; остальные коды описываются явно. Инварианты расчёта (трасса — граф
  с источниками, окупаемость = CAPEX/эффект, поток по годам = поток по месяцам, N = база + резерв) проверяются на
  демо-проектах всех трёх типов объектов (`test_invariants_api.py`), а не только на складе.
- **Почему.** Фронт генерирует типы из контракта, и ошибки, найденные фронтом 23.09, были расхождениями «бэкенд
  отдаёт `null`, контракт обещает значение». Аудит нашёл 25 таких полей и разрыв трассы у уборки в аэропорту
  и больнице, которого не видели тесты на складе.
- **Альтернативы.** Schemathesis (генерация запросов по контракту) — дольше в CI и не проходит сценарии
  с состоянием; проверка только «операции есть в контракте» (как было) не ловит форму ответа.

### D-021 · 2026-09-23 · Отчёты: одна модель данных, три формата, Excel с живыми формулами
- **Решение.** Отчёт — фоновая задача: `service/reports/collect.py` собирает `ReportModel` (домен), рендеры
  в `infra/reports/` работают без БД.
  - **Сбор.** Устаревшие сценарии перед сборкой пересчитываются. В отчёт входят параметры с происхождением,
    подбор (топ-3 на процесс), состав и N, экономика с формулами, сравнение, риски (торнадо, Монте-Карло с seed 1,
    «что замерить») рекомендованного сценария, планировка и последняя имитация и перебор, нормативы, источники
    и ограничения.
  - **PDF.** ReportLab и графики matplotlib. Шрифт DejaVu берётся из данных matplotlib, поэтому кириллица работает
    без системных пакетов. На каждой странице оговорка «предварительная оценка».
  - **Excel.** Каждый шаг трассы переводится в формулу Excel (`infra/reports/formulas.py`). Перевод проверяется
    вычислением: формула, которая не даёт значение платформы, пишется числом, и лист помечает её «нет».
    Лист потока считает NPV и IRR формулами от ставки листа расчёта. Сверка пересчётом в LibreOffice:
    145 из 145 формул и NPV/IRR совпадают с платформой.
  - **Форматы.** `json` — та же модель для отладки и интеграций; `docx` отложен (422).
- **Почему.** ТЗ требует отчёт с прозрачным расчётом. Живые формулы дают жюри поменять вход и увидеть, что
  платформа считает так же. Одна модель данных для всех форматов исключает расхождение цифр между ними.
- **Альтернативы.**
  - HTML → PDF (WeasyPrint) требует системных библиотек в образе — отвергнуто.
  - Excel только со значениями не показывает, откуда число. Оставлен как опция `live_formulas: false`.

### D-020 · 2026-09-23 · Дизайн фронта — язык прототипа v0, 3D-двойник возвращается как витрина
- **Решение.** Визуальная основа нового `frontend/` — прототип v0 (`legacy/frontend-v0/`): светлый холст, чёрные
  кнопки, синий только акцент, крупные заголовки-выводы («77 % ФОТ — отбор заказов»), нумерованные шаги в верхней
  панели, экран шага «Шаг N из 9 · вопрос» с переходами назад/дальше, пилюли, полосы, анимированные KPI
  (framer-motion). Тёмная тема от 23.09 отменена по запросу пользователя. 3D-двойник (three / r3f) перенесён в
  `widgets/twin` и живёт на двух экранах: «Объект» (обзор типовой планировки) и «Имитация» (роботы, очередь на
  приёмке, тона зон — только из сводки прогона бэкенда). Экран имитации работает на реальных эндпоинтах:
  запуск прогона с `fleet_override`, опрос статуса, таймлайн очереди, «расчёт против имитации», узкое место,
  перебор флота, который записывает N в сценарий.
- **Почему.** Пользователь: «за основу бери дизайн v0, обязательно оставь 3D-карту». Обязательная 2D-карта на
  данных планировки (D-006) остаётся на шаге «Планировка»; 3D — иллюстративная сцена с типовой геометрией, расчёты
  и число роботов она не меняет — это делает перебор флота (D-007, D-019).
- **Альтернативы.** Оставить тёмную панель (отвергнуто пользователем); 3D по реальной геометрии планировки — позже,
  на тех же событиях, что и 2D-плеер.

### D-019 · 2026-09-23 · Имитация: устройство модели и как она меняет N
- **Решение.** DES на SimPy по графу планировки (`engine/simulation/`), развитие D-007.
  - **Ресурсы.** Однополосный рабочий проход (участок между проездами) — ресурс на 1 робота
    (`sim_aisle_capacity_robots`), так появляются заторы. Ресурсами также служат ворота при погрузке, станции G2P
    и зарядки. Число зарядок берётся из расчёта сценария и делится между местами зарядки на схеме.
  - **Задачи.** Паллеты приходят фурами по слотам записи на ворота (`sim_truck_pallets`, фура приходит в случайный
    момент своего слота) и появляются у ворот в темпе разгрузки. Строки отбора приходят пуассоновским потоком
    и собираются в рейсы стеллажа. Обычный день — пиковое окно `sim_peak_window_hours`, пиковый режим — пиковая
    интенсивность без передышки.
  - **Робот.** Ближайший свободный робот берёт задачу. Батарея разряжается от работы, на зарядку он уходит
    по порогу `sim_charge_threshold_share`. Учитываются отказы (MTBF и заданные вручную) и выезд из прохода
    перед простоем. Задачу, ждущую дольше `sim_human_takeover_wait_min`, забирают люди.
  - **KPI.** Окно измерения — после разогрева и до «конец − норматив». Сводка: SLA, загрузка по состояниям,
    очередь, заторы, узкое место (ресурс с наибольшей загрузкой выше `sim_bottleneck_utilization`),
    сверка «расчёт против имитации» по той же формуле производительности.
  - **Общие случайные числа.** Отдельные потоки для прибытий, ячеек и отказов: прогоны с разным N видят один и тот
    же день.
  - **Перебор флота.** Ищет минимальное N со средним SLA по `sim_replications` повторам не ниже цели. Поиск стартует
    с оценки по первому прогону, дальше — шагами с удвоением и делением пополам. Ответ записывается в позицию
    сценария и действует, пока не изменилась версия проекта. Расчёт берёт `simulated + резерв`, покрытие пика
    при этом равно 1.
  - **Исполнение.** Прогон хранит свой вход и планировку. В docker его выполняет воркер arq, локально и в тестах —
    процесс API после ответа. Какие параметры задают потоки процесса, описано блоком `simulation` в справочнике.
- **Почему.** Жюри проверяет, что имитация влияет на расчёт, и она влияет: на демо-складе 8 + 2 AMR вместо 14 + 3.
  Робот берёт следующую задачу рядом, и пустой пробег короче «2 × L». Имитация нашла и две ошибки аналитики:
  стоянку G2P-робота у станции и станции без запаса по загрузке. Обе исправлены в формулах.
- **Альтернативы.**
  - Имитация без пространства (очередь, как в v0) не даёт заторов и узких мест — отвергнуто.
  - Агентная модель с физикой движения — избыточно для экспресс-оценки.
  - Имитация уборки и тягачей — пока нет, их N остаётся по расчёту (`skipped_processes`).

### D-017 · 2026-09-23 · Планировка склада — схема из параметров и граф маршрутов для цикла и имитации
- **Решение.** Генератор строит схему склада (не CAD) по параметрам объекта и нормативам категории `layout`.
  Каждый размер — шаг трассы `derivation` с формулой и источником. Состав схемы: здание, ярусы, проходы и поперечные
  проезды, ворота, зона G2P со станциями, зарядки, упаковка. По графу Дейкстрой считаются средние маршруты
  (`stats.avg_route_m`), и в расчёт они входят как входы вида `layout`.
  - **Порядок источников длины маршрута:** замер пользователя (`pallet_route_length_m`) → планировка → норматив
    (200 м ФЦ БАС, 40 м G2P).
  - **Паллеты:** маршрут — среднее по приёмке, отгрузке и внутренним перемещениям, взвешенное объёмами
    (выражение в справочнике процесса). Хранение случайное: ячейки взвешены по паллетоместам.
  - **Схема по умолчанию:** U-flow, приёмка и отгрузка на одном фасаде. Ворота стоят по центру своей половины блока
    стеллажей, зарядки — между приёмкой и отгрузкой. Число ворот — по пиковому потоку паллет, если в параметрах его нет.
    Паллетные роботы не срезают путь через зону G2P.
  - **Демо-склад создаётся с планировкой.** Перегенерация или правка повышает версию проекта, и расчёты становятся stale.
    После правки в редакторе длины рёбер пересчитываются по координатам, а `generated` = false.
  - **Подложка-план** хранится в Postgres (`stored_files`), чтобы `docker compose up` не требовал S3.
- **Почему.** Норматив 200 м — маршрут чужого объекта. Схема даёт маршрут этого склада, а граф с ширинами и
  вместимостями рёбер нужен имитации (D-007). На демо-складе маршрут 95 м вместо 200 м, и паллеты окупаются
  за 3 года (`docs/DATA.md`).
- **Альтернативы.**
  - Оставить норматив и множитель √площади из v0 — это не маршрут, отвергнуто.
  - Хранение по классам ABC — позже, если будет время: оно даёт более короткий маршрут, а случайное хранение
    консервативно.
  - Импорт DWG/DXF — вне рамок, у нас подложка и редактор.

### D-015 · 2026-09-22 · Экономическая модель сценария
- **Решение.** Сценарий — портфель «процесс → продукт → N». Все суммы с НДС (единая база, Q&A 16.09), до налога
  на прибыль.
- **Годовые статьи** (год 1).
  - CAPEX (покупка, лизинг): роботы, зарядки и станции G2P, доставка, лицензии RMS, ПНР, статьи объекта из справочника
    (`site_costs`: интеграция, разметка, Wi-Fi, лифты, обучение), резерв CAPEX.
  - CAPEX (RaaS): подключение + статьи объекта.
  - OPEX: сервис, расходники, подписка ПО, АКБ (в среднем за год), электроэнергия, персонал эксплуатации (не меньше
    минимума на объект), связь; у RaaS — абонентская плата: своя ставка из ТТХ или max(доля цены, норматив).
- **Эффект.** Высвобождение = ФОТ процесса × доля высвобождения × доля пика, закрытая парком. Сверху его ограничивает
  потолок: человеко-часы самого объёма работ при ручном выполнении. Выработка человека берётся из норматива (уборка,
  отбор); для транспорта — не выше цикла робота. Причина потолка: численность в датасете не связана с объёмами.
  Из высвобождения вычитаются OPEX роботизации и проценты по кредиту или лизингу (Доп. 2.1).
- **Загрузка за рейс.** Задаётся выражением в справочнике процессов: порции отделения, контейнер белья, сцепка тележек
  с учётом их тары. Тягач заменяет только водителя, поэтому его доля высвобождения умножается на `tow_driving_share`.
- **Денежный поток** — помесячный.
  - Внедрение без эффекта, затем разгон: высвобождение растёт линейно, OPEX роботов идёт сразу полностью.
  - Индексация: ФОТ — по зарплатам, прочее — по инфляции.
  - Замены: АКБ по интервалу, парк — по сроку службы; остаточная стоимость (линейно) входит в последний месяц.
  - Кредит и лизинг — аннуитет по номинальной ставке, метод ФЦ БАС. RaaS — плата с запуска; при выкупе после договора
    переходим на OPEX владения.
- **Метрики.**
  - Окупаемость по ТЗ = CAPEX / годовой эффект; дисконтированная — по потоку.
  - ROI = накопленный поток / CAPEX (Q&A: с вычетом CAPEX). NPV и IRR — по месячному потоку.
  - TCO = CAPEX + Σ(оставшийся ФОТ + OPEX + плата RaaS + проценты + замены) за горизонт; у базы — ФОТ всего объекта.
  - Амортизация и налог — только справочно (Доп. 2.2, Q&A).
- **Вердикт** — по интервалам-нормативам (3 / 5 / 7 лет) с проверкой NPV. Риски — по правилам (бюджет, срок службы,
  NPV, покрытие пика, статус продукта, нет имитации, «паспорт против физики»).
- **Калибровка** — модельные кейсы ФЦ БАС (`seeds/data/calibration.yaml`) пересчитываются нашими формулами
  и нормативами, расхождение показывается по статьям.
- **Почему.** ТЗ 3.5 и Доп. 2 целиком. Каждая строка — формула с входами и источниками. Экономика не зависит от того,
  насколько согласован датасет.
- **Альтернативы.**
  - Годовая модель без помесячного потока — теряет внедрение, разгон и точные сроки замен.
  - Высвобождение без потолка — давало окупаемость 0,3 года на данных аэропорта.

### D-014 · 2026-09-22 · Формулы в данных, пустой проект против демо, распределение персонала
- **Решение:** спрос процессов (`demand.per_day / hours_per_day / peak_factor`) и межполевые проверки формы описаны
  в YAML справочника на мини-языке `app/engine/expressions.py`: только имена параметров и нормативов, `+ − × ÷`,
  сравнения, `min/max/coalesce`; **числовые литералы запрещены парсером** — коэффициент не спрятать в формулу (ТЗ 3.5.1).
  Проценты из датасета приходят в формулы долями. Общие группы персонала делятся между процессами долями
  `labor_allocation` с обоснованием (сумма по группе ≤ 1, проверяется при сидировании) — ФОТ не задваивается.
  Пустой проект не подставляет значения демо-объекта организатора в обязательные поля (они описывают один конкретный
  склад) — пользователь вводит свои; допущения команды действуют везде. Демо-проект берёт все значения датасета
  со статусом `default` и источником-листом.
- **Почему:** новый тип объекта = только данные; жюри видит формулу и источник каждого числа; честная панель доверия.
- **Альтернативы:** функции спроса в коде на каждый процесс — отвергнуто (код меняется при каждом объекте).

### D-008 · 2026-09-22 · LLM — везде, где даёт ценность, но никогда в расчётах
- **Решение:** LLM используем для умного импорта, обогащения ТТХ каталога из открытых источников, объяснений
