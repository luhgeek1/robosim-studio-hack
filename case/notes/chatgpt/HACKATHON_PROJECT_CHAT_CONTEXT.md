# 1. Коротко: что это вообще за задача

Команда участвует в хакатоне, связанном с роботизацией.

Смысл задачи в общих чертах: сделать цифровой сервис, который помогает оценить возможность и экономическую целесообразность внедрения робототехнических решений на объекте.

В предоставленных материалах фигурируют три типа объектов:

- склад;
- аэропорт;
- медицинское учреждение.

У пользователя есть параметры объекта, текущие процессы, нагрузка, персонал, ограничения и бюджет.

Система должна помочь перейти от этих исходных данных к осмысленному варианту роботизации.

В центре задачи находятся примерно такие вопросы:

- какие робототехнические решения вообще подходят этому объекту;
- какие решения не подходят и почему;
- сколько единиц техники понадобится;
- сколько это будет стоить;
- какие будут CAPEX/OPEX;
- как будет выглядеть экономический эффект;
- какой срок окупаемости;
- сможет ли выбранная конфигурация выполнять требуемый объём операций;
- как сравнить несколько сценариев.

То есть задача значительно шире, чем просто «сделать каталог роботов».

# 13. Наше рабочее направление: RoboScope

Для удобства обсуждения мы временно называли концепт **RoboScope**.

Идея:

> сервис, который по данным объекта помогает определить, какой робот нужен, сколько единиц потребуется, насколько выгодно внедрение и справится ли выбранная конфигурация с нагрузкой.

> **Какой робот → сколько → выгодно ли → справится ли.**

Это только продуктовая формулировка из brainstorm.

# 15. Идея Smart Import

Одна из сильных идей, которую мы обсуждали:

пользователь **не обязан заполнять идеальный шаблон**.

Он может загрузить существующий файл компании:

- Excel;
- CSV;
- JSON;
- PDF;
- текстовую таблицу;
- другой полуструктурированный формат.

LLM пытается сопоставить данные с внутренней схемой.

Пример:

```text
«рабочий коридор 3200 мм»
```

может быть приведён к:

```json
{
  "aisle_width_m": 3.2
}
```

При этом мы пришли к важному архитектурному принципу:

> **LLM нормализует и объясняет, но не выполняет критичные расчёты.**

То есть:

LLM:
- извлекает;
- сопоставляет;
- понимает подписи;
- приводит единицы;
- объясняет.

Обычный код:
- валидирует;
- считает;
- фильтрует;
- рассчитывает экономику;
- запускает симуляцию.

# 16. Почему мы так разделили LLM и расчёты

Идея была в том, чтобы избежать ситуации, когда ROI или количество роботов зависит от ответа генеративной модели.

Например:

```text
файл клиента
→ LLM normalization
→ structured JSON
→ Pydantic / rules
→ calculation engine
```

Это делает решение:

- объяснимее;
- воспроизводимее;
- устойчивее к hallucinations;
- проще для защиты перед экспертами.

# 17. Идея Data Confidence

Мы обсуждали, что у данных может быть разный уровень качества.

Для каждого параметра теоретически можно хранить:

```text
value
unit
source
source_value
confidence
is_assumption
```

Пример в UI:

```text
Data Confidence: 91%

✓ площадь склада — подтверждено
✓ ширина проходов — подтверждено
⚠ стоимость обслуживания — оценка
⚠ пиковая нагрузка — допущение
```

Почему это показалось полезным:

- каталог сам по себе неполный;
- корпоративные входные файлы могут быть неоднородными;
- пользователь должен понимать, насколько можно доверять результату.

Это **опциональная продуктовая идея**, не обязательный критерий.

# 18. Идея explainable matching

Вместо «нейросеть выбрала Robot X» мы обсуждали двухэтапный подход.

## Hard constraints

Сначала обычные ограничения:

```text
payload >= required payload
robot dimensions fit aisle
environment supported
budget acceptable
```

Если критичное условие не выполняется — решение исключается.

## Soft score

После этого оставшиеся решения можно ранжировать, например по:

- производительности;
- цене;
- совместимости;
- зрелости;
- кейсам;
- качеству данных.

Пользователь должен видеть:

```text
Почему подходит
Почему не подходит
Какие ограничения
```

Веса scoring не были утверждены.

# 19. Идея автоматического расчёта количества роботов

Мы обсуждали, что система должна по возможности сама отвечать на вопрос:

> «Мне нужно 2, 3 или 10 роботов?»

Упрощённый расчёт:

```text
требуемый throughput
/
эффективный throughput одного робота
=
первичная оценка количества
```

С поправками на:

- пики;
- загрузку;
- простои;
- зарядку;
- резерв.

Затем это количество можно проверить симуляцией.


# 22. Идея 3D digital twin

Пользователю понравилась идея сделать эффектную 3D-визуализацию объекта.

Мы обсуждали вариант **digital twin-lite**, а не настоящий инженерный digital twin.

То есть в 3D могут быть:

- помещение;
- стеллажи;
- приёмка;
- хранение;
- комплектация;
- отгрузка;
- зарядная зона;
- роботы;
- паллеты;
- маршруты;
- очереди;
- bottleneck'и.

Главная мысль:

> 3D нужно не ради красоты, а чтобы предприниматель визуально увидел результат сценария.

# 25. Предлагаемый demo moment

Мы представляли защиту примерно так:

1. На экране склад с тремя роботами.
2. Система показывает, что SLA выполняется.
3. Пользователь переключается на два робота.
4. Один робот исчезает из 3D.
5. Оставшиеся начинают работать почти постоянно.
6. В зоне приёмки растёт очередь.
7. Появляется bottleneck.
8. SLA падает.
9. Система объясняет, что конфигурация не выдерживает пик.
10. Пользователь возвращает три робота.
11. Очередь уменьшается.
12. KPI восстанавливаются.
13. Система объясняет, почему три робота — минимально достаточная конфигурация.

Опять же, это только возможный сценарий эффектной защиты.

# 26. Normal Load / Peak Load

Ещё одна обсуждавшаяся идея:

переключатель:

```text
Normal
Peak
```

На Peak Load:

- больше задач;
- длиннее очереди;
- выше utilization;
- могут появляться bottleneck'и;
- SLA ухудшается.

Это хорошо визуализирует необходимость учитывать не только среднюю, но и пиковую нагрузку.
